# 로컬 기능 검증

사용 중인 Balearn 환경과 별도 Docker 프로젝트를 사용한다. Chrome 새 컨텍스트마다 Keycloak 임시 계정을 만들어 소유자, 멤버, 비회원 흐름을 검증한다. 테스트는 실제 OIDC 인가 코드와 Balearn 토큰을 사용한다.

## 범위

| 화면·기능 | 확인 방법 |
|---|---|
| 로그인·계정 | Chrome의 조직 계정 버튼부터 대시보드 진입까지 검증. API로 토큰 갱신, 사용자 조회·수정, 프로필 이미지, 계정 삭제와 로그아웃 후 기존 토큰 거부를 확인 |
| 모임과 설정 | 모임 생성·조회·변경·삭제, 초대·가입·탈퇴, 팀 프로필 수정, 권한 변경·소유권 이전·멤버 제거, 비회원 및 비로그인 접근 거부 |
| 대시보드·캘린더·성취 | 목표와 일정 생성·조회·수정·삭제, 월·주·오늘 조회 결과, 미션 완료·일괄 변경·취소, 순위 점수 |
| 공지와 자료 | 공지 생성·조회·수정·삭제, 자료 등록·목록·상세·다운로드·삭제, 원본 바이트 비교, 비회원·미인증 및 이전 공개 경로의 차단 |
| 채팅 | 별도 계정 두 개의 STOMP 송수신, REST 이력, Elasticsearch 예약 적재 후 중복 여부 |
| 화면 렌더링 | Chrome에서 로그인 이후 대시보드·달력·성취·자료·채팅·설정의 11개 경로 진입, 클라이언트 예외와 실패한 API·이미지 응답 확인 |

## 다시 실행

Windows에 Docker Desktop, Node.js 및 기본 위치의 Chrome이 필요하다. 두 저장소와 Compose 파일이 있는 상위 폴더에서 실행한다.

```powershell
$env:BALEARN_API_PORT = '38080'
$env:BALEARN_IDP_PORT = '38180'
$env:FRONTEND_URL = 'http://localhost:33000'
$env:OIDC_CLIENT_SECRET = [guid]::NewGuid().ToString('N')
$env:BALEARN_IDP_ADMIN_PASSWORD = [guid]::NewGuid().ToString('N')
docker compose -p balearn-feature-qa -f compose.balearn-local.yml -f compose.balearn-oidc.yml up -d

npm.cmd install --prefix "$env:TEMP\balearn-feature-qa" --no-audit --no-fund playwright-core@1.65.1
docker build --build-arg NEXT_PUBLIC_API_URL=http://localhost:38080 --build-arg NEXT_PUBLIC_LOGIN_PROVIDERS=oidc -t balearn-feature-qa-frontend balearn-fe
docker run -d --rm --name balearn-feature-qa-frontend -p 127.0.0.1:33000:3000 balearn-feature-qa-frontend
```

`http://localhost:38080/actuator/health`가 `UP`을 반환하고 프런트엔드에 접속할 수 있으면 `node deployment/feature-qa.mjs`를 실행한다. 실패가 있으면 종료 코드는 1이다. 같은 검증 환경을 재기동할 때에는 첫 실행의 OIDC 시크릿과 관리자 비밀번호를 사용한다.

테스트 범위에는 이메일이나 소셜 제공자의 실제 외부 서비스, 브라우저 호환성 전수 조합, 모바일·오프라인 설치, 부하·장애 복구 테스트가 포함되지 않는다. 로그인과 화면 진입은 브라우저에서 실행했고, 생성·수정·삭제의 상태 변화는 주로 API에서 확인했다.

## 발견 사항

최초 상세 검증은 30개 점검 중 28개 통과, 2개 실패였다. 아래 변경을 반영한 새 빌드에서 재실행한 결과 **30개 모두 통과**했다. 이전 로컬 다운로드 URL은 삭제 후 404를 반환했고, Chrome 로그아웃 후 접근 토큰과 갱신 쿠키 재사용이 각각 거부됐다. 실제 GCS 버킷과 CDN에서 삭제 및 캐시 무효화는 검증 범위에 포함되지 않았다.

- **수정 및 재검증** · 프런트엔드와 백엔드를 각각 컨테이너로 실행하고 공개 API 주소가 루프백이면 이미지 최적화 서버가 자신의 컨테이너에서 API를 찾았다. 루프백 설정에서는 브라우저가 원본 이미지를 직접 받도록 변경했다. Chrome 페이지와 이미지 디코딩 검증이 통과했다.
- **수정 및 재검증** · 리더보드의 개인 점수와 순위가 사용자 ID로 조회되고, 기록은 모임 멤버 ID로 저장됐다. 조회에도 모임 멤버 ID를 사용하도록 수정했다. 두 ID가 다른 계정으로 점수 증가, 일괄 변경, 취소를 검증했다.
- **수정** · 자료 삭제가 DB의 행만 제거해 기존 다운로드 주소가 열렸다. 개별 자료 삭제에서 해당 URL을 소유한 저장소의 객체도 삭제한다. 연결할 수 없는 저장소의 자료는 삭제 성공으로 응답하지 않으며 DB 트랜잭션을 롤백한다.
- **수정** · 화면 로그아웃이 브라우저 상태만 지웠다. 서버 로그아웃이 성공하면 세션·모임·쿼리 상태를 지우고 로그인 화면으로 돌아간다. 회귀 검증은 기존 접근 토큰과 갱신 쿠키가 거부되는지 확인한다.

## 다음 검증 목록

아래 항목은 미실행이다. 변경 이후에는 기존 30개 점검을 다시 실행하고, 추가 검증은 다음 순서로 진행한다.

### 1. 다음 변경부터 자동화

- [ ] **CI 회귀 테스트** · 깨끗한 환경에서 FE 빌드, BE 테스트, 격리 Compose의 기능 검사 30개를 실행한다. 모든 검사가 통과해야 하며, 실패한 경우 시나리오 이름과 서비스 로그를 남겨 같은 커밋에서 재현할 수 있어야 한다.
- [ ] **브라우저에서 기능 완료** · 로그인 → 모임 생성 → 다른 계정 초대·가입 → 일정·미션 등록 → 자료 업로드·삭제 → 채팅 → 로그아웃을 메뉴와 폼으로 진행한다. 새로고침 후에도 화면에 저장 결과가 표시되고 브라우저에서 두 계정의 상태가 섞이지 않아야 한다.
- [ ] **권한과 세션** · 두 모임을 만들고 소유자·리더·멤버·비회원의 허용·거부 결과를 화면과 API에서 대조한다. 토큰 만료, 탭 두 개에서의 로그아웃, 로그아웃 요청 실패 후 재시도까지 확인한다. 실패한 요청은 데이터를 바꾸지 않아야 한다.
- [ ] **경계값과 중복 요청** · 자정·월말·연말에 오늘·주간·월간 일정이 일관되게 표시되는지 확인한다. 초대 만료와 중복 가입, 미션 완료·취소 연속 요청, 업로드 허용 형식·크기 경계에서 데이터와 점수가 중복 반영되지 않아야 한다.

### 2. 온프레미스 배포 전

- [ ] **같은 구성으로 사전 배포** · 운영에 사용할 TLS 프록시, 도메인, OIDC 및 영구 볼륨을 준비한 뒤 로그인 콜백·쿠키, WebSocket 연결, 업로드와 기존 URL을 확인한다. 서비스 재시작 후 데이터와 파일이 유지돼야 한다.
- [ ] **백업 복원과 이전** · MySQL·Redis·Elasticsearch·미디어·IdP의 백업을 빈 스택에 복원한다. 과거 DB 스키마에서도 기존 계정 로그인, 모임 권한, 자료 원본, 채팅 이력이 맞는지 확인하고 실제 복구 시간과 복구 시점을 기록한다.
- [ ] **장애와 재연결** · 테스트 환경에서 Redis·Elasticsearch·파일 저장소를 잠시 중지한다. 화면에 실패가 표시되고, 복구 후 재시도에서 채팅 누락·중복 또는 자료 목록과 원본의 불일치가 발생하는지 확인한다. 개별 자료 삭제와 모임 삭제를 각각 검증한다.
- [ ] **모바일·PWA** · Android Chrome과 iOS Safari에서 로그인, 캘린더, 파일 선택, 채팅을 확인한다. 오프라인과 서비스 워커 갱신 후에도 이전 계정의 정보가 표시되지 않고, 다시 연결했을 때 최신 화면으로 돌아와야 한다.

### 3. 클라우드 전환과 수평 확장 시

- [ ] **GCS와 CDN** · 별도 버킷에서 업로드·다운로드·삭제를 확인한다. 원본과 CDN의 응답을 각각 확인하고, 삭제 권한이 없을 때 자료 기록이 유지되는지 검증한다. 이전 URL이나 잔여 객체 정리는 사본에서 대상을 먼저 대조한다.
- [ ] **제공자 전환과 롤백** · 로컬에서 GCS로 바꾸고 되돌리는 동안 기존·신규 파일이 열리는지 비교한다. Kakao·Google·GitHub 중 배포에서 활성화할 제공자는 실제 콜백 및 토큰 갱신까지 검증한다.
- [ ] **복제본과 부하** · 백엔드 두 인스턴스에서 로그인, 채팅 재연결과 예약 적재를 확인한다. 예상 동시 접속과 업로드 크기 기준으로 응답 시간·오류율을 기록하고, 정상 부하 기준을 정한 뒤 배포 전후를 비교한다.

검증 결과에는 실행 날짜, 커밋, 환경, 통과·실패·미실행, 재현 방법을 남긴다. 배포 설정과 데이터 이전 절차는 [배포 가이드](DEPLOYMENT.md)에서 확인한다.
